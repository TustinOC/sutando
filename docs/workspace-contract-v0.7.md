# Workspace Contract v0.7

**Status**: design proposal, 2026-05-31 22:00Z. Self-contained spec; integrates v0.6 (design-locked 2026-05-30) + naming-iteration (2026-05-31) + cwd-overlay extension (2026-05-31). Supersedes `workspace-contract-v0.6.md`, `workspace-contract-v0.6-naming-iteration.md`, and `workspace-contract-v0.7-overlay-proposal.md` — those three drafts remain in `notes/` as the iteration history.

**One-sentence summary**: v0.7 organizes a Sutando user's per-user workspace along two orthogonal axes — **tier** (durability + sync) and **scope** (collaboration boundary) — so a single workspace holds the user's personal data AND any number of room subscriptions, with read-union making room knowledge automatically available to the personal agent; directory names drop the `_agent` / `_machine` / `_room` suffix (tier inferred from parent path); an **opt-in cwd-overlay** brings AGENT/MACHINE/ROOM content into the agent's cwd subtree so Claude Code's native skill / command / MCP / plugin discovery activates over workspace content.

---

## Part 1. Problem and framing

Sutando's per-user workspace stores three classes of state that have to be managed independently: **runtime data** (live tasks, ephemeral state — never leaves this disk), **per-machine state** (host-specific configuration that syncs between the user's own devices), and **agent-level knowledge** (notes, memory, skills shared across all the user's devices).

That works for a single user managing their own stuff. What was missing: **the user collaborates**. They join rooms, take notes with teammates, accumulate knowledge that should benefit their personal agent without polluting their private memory.

A second gap surfaced in the v0.6 conversation: keeping workspace fully outside the launch cwd **forecloses 7 content-anchored Claude Code privileges** (CLAUDE.md auto-discovery, `.claude/settings.json` layering, project skills / commands / agents, `.mcp.json`, plugin discovery). v0.7 adds an **opt-in cwd-overlay** that brings workspace content into the cwd subtree so those native mechanisms activate over workspace-supplied data.

v0.7's goal: organize the contract so a workspace can hold N rooms in parallel with personal data, sync each independently, present a unified knowledge surface to the agent at read time, AND optionally surface its content to Claude Code's native cwd-anchored discovery — preserving the three-class state separation, the scope-tier 2-axis model, and the multi-writer architecture v0.6 protects.

### 1.1 The clean mental model (owner-coined 2026-05-29, refined 2026-05-31)

> **`hosts/` is physical context, `rooms/` is virtual context.**
> **Tier is the path the data lives in, not a suffix on the directory name.**

The workspace root sits between hosts/ and rooms/ as YOU (the personal agent). Two subdirectories represent orthogonal axes of agent state:

| Concept | Dimension | What lives under it |
|---|---|---|
| `hosts/<H>/` | **Physical / material** | Per-machine slices for devices you own. Identity = hostname. |
| `rooms/<X>/` | **Virtual / social** | Per-collaboration slices for spaces you join. Identity = `room_id`. |
| (workspace root) | **You** | Personal agent — single user identity participating in both physical AND virtual contexts. |

The path location encodes the tier:

| Path you walked into | Tier |
|---|---|
| `hosts/<H>/local/` | LOCAL |
| `hosts/<H>/` (but not under `local/`) | MACHINE |
| `rooms/<X>/` | ROOM |
| (none of the above; workspace root) | AGENT |

This framing makes invariants obvious:
- Host slices sync only between your own devices (physical context is private to you).
- Room slices sync with all room members (virtual context is collaborative by definition).
- Both stay anchored to **you** (`identity_agent.json` at workspace root) — one identity, many hosts, many rooms.

## Part 2. The contract

### §2.0 Agent-digestible summary

Put this in `$SUTANDO_REPO_DIR/sutando/CLAUDE.md` under `## Workspace contract (v0.7)`:

```
$SUTANDO_WORKSPACE/                  ← workspace root = personal scope (implicit; YOU)
├── identity_agent.json              ← user identity (+ rooms registry; file keeps suffix)
├── CLAUDE.md                        ← agent orient (auto-generated by sync engine)
├── memory/, notes/, skills/, context/, assets/, logs/
│                                    ← AGENT (personal; cross-host within YOU)
├── public/                          ← publishable content (carve-out from default-private)
│   └── memory/, notes/, blog/, ... ← bots may quote with `[from $WORKSPACE/public/]` attribution
│
├── hosts/<hostname>/                ← per-host slices (physical context)
│   ├── identity_machine.json
│   ├── memory/, notes/, skills/, context/, logs/
│   │                                ← MACHINE (this host only)
│   ├── tasks/, results/             ← MACHINE (this host's cross-host-visible task log)
│   └── local/                       ← LOCAL (this disk only, NEVER syncs)
│       └── state/, tasks/, results/, logs/, secrets/, notes/, context/, memory/
│
├── machine -> hosts/<this-hostname>/   ← stable local alias
│
└── rooms/<room-id>/                 ← per-room slices (virtual context)
    ├── identity_room.json           ← room manifest (immutable room_id + members[] + membership privacy)
    ├── memory/, notes/, skills/, context/, assets/, logs/
    │                                ← ROOM content (member-only)
    ├── public/                      ← room's publishable content
    │   └── (papers, posts, anything room agreed to publish externally)
    ├── tasks/<member-id>/, results/<member-id>/  ← per-member partition
    └── members/<member-id>/         ← per-member free-form slice (each member writes own)
```

**Cross-host task/result visibility**: there is no root-level `tasks/` aggregate at the workspace root. Each host writes its task log under `hosts/<H>/tasks/` (MACHINE). Read-union (§2.5.3) walks `hosts/*/tasks/` at agent-context-load time so the agent sees every host's task history as one merged view.

**Where do I write?**

| Concern | Path | Tier |
|---|---|---|
| Live task → core agent | `machine/local/tasks/task-{ts}.txt` | LOCAL |
| Result ← core agent | `machine/local/results/task-{ts}.txt` | LOCAL |
| Runtime state | `machine/local/state/` | LOCAL |
| Secrets | `machine/local/secrets/` (never tracked) | LOCAL |
| Host-specific note | `machine/notes/<name>.md` | MACHINE |
| Cross-host fact (personal) | `memory/<slug>.md` | AGENT |
| Cross-host note (personal) | `notes/<name>.md` | AGENT |
| Room-shared fact | `rooms/<X>/memory/<slug>.md` | ROOM |
| My contribution to room X | `rooms/<X>/members/<my-id>/...` | ROOM (write-partitioned) |

**Hard rules**:
1. **Read-union, write-scoped** for AGENT and ROOM tiers (see §2.5.3). Sync engine writes per-scope; agent context loader reads union across scopes.
2. **LOCAL never syncs**. Path-pattern-gated via `.gitignore`.
3. **Each scope is its own git repo**. Personal vault for workspace root; room vault per `rooms/<X>/`.
4. **Secrets never tracked**. Push-gate scans every push; matches abort.
5. **Private zone never appears in public outputs**. Workspace data + Discord DMs + private channels + email + internal designs are private. PRs / issues / commit messages / comments / public Discord channels / tweets are public. Bots drafting public output must paraphrase, never quote, private-zone content. See §2.2.1 for the full zone table.
6. **Tier is inferred from path location, never from a directory-name suffix**. Files keep `identity_<scope>.json` suffix for grep-ability across the whole tree; directories do not.

### §2.2 Two-space split — `SUTANDO_REPO_DIR` vs `SUTANDO_WORKSPACE`

Two distinct directories, two distinct concerns:

- **`SUTANDO_REPO_DIR`** — the Sutando source repo checkout. Holds code, skills source, project rules, CLAUDE.md. Pushed to the public/shared `sutando` GitHub repo.
- **`SUTANDO_WORKSPACE`** — per-user mutable state. Holds personal/room/host data. Pushed to private vaults (one personal + N room).

Resolution (every service reads the same):
1. `$SUTANDO_WORKSPACE` env var (override; `~` is expanded).
2. `~/.sutando/workspace/` (default).

`SUTANDO_REPO_DIR` is separate — names the public-repo checkout for scripts like `sync-engine.sh` and `session-handoff.sh` that need the source tree. Do NOT conflate.

**Helper functions** (do not reinvent):
- Python: `from workspace_default import resolve_workspace` → `Path`.
- TypeScript: `import { resolveWorkspace } from './workspace_default.js'` → `string`.
- Swift: `AppDelegate.workspace` property.

#### §2.2.1 Private zone vs public zone

The repo-vs-workspace split is the headline boundary, but the *operational* private/public boundary is wider than just paths on disk. Bots and agents authoring content for any of the public surfaces below must paraphrase, never quote, anything that came from a private surface.

| Surface | Private | Public |
|---|---|---|
| `$SUTANDO_WORKSPACE/**` | ✅ | — |
| Discord DMs (owner DM, team DM) | ✅ | — |
| Discord private channels (owner ↔ team) | ✅ | — |
| Email content (received + drafts) | ✅ | — |
| Internal designs / pre-publication notes | ✅ | — |
| GitHub PRs / issues / commits / comments | — | ✅ |
| Public Discord channels (open server channels) | — | ✅ |
| Tweets / blog posts / website copy | — | ✅ |

**Bot rule**: when drafting content for a public surface, you may *use* private-zone content as reasoning context but must NOT paste verbatim. The single exception is the `public/` subdir convention (below) — content inside any `public/` folder is publish-ready and may be quoted with attribution. Paraphrase, summarize, or redact PII / specifics elsewhere. If unsure, ask the principal before posting.

**Privacy default by tier** (workspace-internal):

| Tier | Privacy default | Publishability override | Bot-behavior note |
|---|---|---|---|
| **LOCAL** | ALWAYS private | None — `public/` does NOT exist under LOCAL | Two-layer: sync-private (never leaves disk via gitignore) AND author-private (bots never quote verbatim). Includes secrets, raw task bodies, runtime state. |
| **MACHINE** | Private | None recommended | Per-host slice; only YOU see it across YOUR devices. Not for public quoting. |
| **AGENT** | Private | `$WORKSPACE/public/` is the publishable carve-out | Bot paraphrases AGENT-tier content for public output; may quote `public/` content with `[from $WORKSPACE/public/]` attribution. |
| **ROOM** | Private (members only) | `rooms/<X>/public/` is the room's publishable carve-out | Bot paraphrases ROOM content; may quote `rooms/<X>/public/` with `[from room <name>/public/]` attribution. |

LOCAL is the strictest — even `PERSONAL_CLAUDE.md` and other internal references must not embed verbatim LOCAL content. The tier-privacy ordering (LOCAL > MACHINE > AGENT-member-only > ROOM-member-only > AGENT-public / ROOM-public) defines the bot's quotability ladder. Inside any tier, the `public/` subdir is the one explicit publishability carve-out.

**Quotability rule of thumb**: a bot drafting a PR / public Discord post / tweet may include verbatim content if and only if the source path contains `/public/` AND the path lives under AGENT or ROOM tier. Everything else must be paraphrased.

**Room membership privacy** (separate axis from content privacy): `identity_room.json` carries a `privacy: "private" | "public"` attribute describing **who can join the room**. `"private"` = invite-only; `"public"` = discoverable / open enrollment. This is orthogonal to the `public/` content folder — a private-membership room can still publish content via `rooms/<X>/public/`, and a public-membership room can keep most of its content member-only with select items in `public/`.

**Why this matters**: Susan flagged on 2026-05-30 that Lucy bot was including Discord DM content in PRs / issue comments. Same risk applies to every bot in the fleet. The rule belongs at the contract level because it governs ALL bot writes, not just one bot's prompt.

### §2.3 Notation — scope and tier

Two orthogonal axes:

**Scope** (path prefix) — the COLLABORATION boundary:
- `personal` — implicit at workspace root (no `personal/` wrapper; root files ARE the personal scope)
- `<room-id>` — at `rooms/<room-id>/`, one per subscribed room

**Tier** (inferred from path location, NOT from a directory-name suffix):
- **LOCAL** — `hosts/<H>/local/**` — this disk only, NEVER syncs. Runtime state, secrets, live queues.
- **MACHINE** — `hosts/<H>/<concept>/` (directly under host dir, NOT under `local/`) — per-host slice; this host's slice syncs cross-host within YOU.
- **AGENT** — root-level `<concept>/` (personal) OR `rooms/<X>/<concept>/` (room) — cross-host or cross-member shared. The TIER NAME (AGENT vs ROOM) differs by scope: personal-scope AGENT = "this user across hosts"; room-scope content uses tier name ROOM = "all room members across their hosts."
- **ROOM** — same path shape as AGENT but under a room scope.

Tier names are independent of numeric ordering: each name says what the data is and who sees it.

**Identity files keep their scope suffix** for grep-ability across the whole tree:
- `identity_agent.json` at workspace root
- `identity_machine.json` under `hosts/<H>/`
- `identity_room.json` under `rooms/<X>/`
- `identity_member.json` under `rooms/<X>/members/<id>/`

(Files keep the suffix; directories drop it. Files are grep'd individually across the workspace; directories are walked hierarchically.)

**`t_s(f)` lift operator**: the explicit promotion action `lift(file, from_tier, to_tier)`. Most lifts are LOCAL ↔ MACHINE ↔ AGENT, or between ROOM and AGENT (see §2.5.4 for automatic demotion = lift on conflict).

### §2.4 Promotion via example skills

The sync engine ships layout + ensure invariants. Concrete lift operations (LOCAL → MACHINE, MACHINE → AGENT, ROOM → AGENT) live in dedicated skills. Two reserved slots:

- `workspace_promotion_skill_agent` — examples of lifting between personal and room scopes.

### §2.5 Sync engine — the converged design

Single converged engine `sync-engine.sh`. Five modes: `sync` / `pull` / `push` / `migrate` / `status`. Opt-in via `SUTANDO_WORKSPACE_SYNC=on`. Privacy-first: defaults off.

#### §2.5.1 Per-scope sync target

Each scope is a SEPARATE git repo, synced independently:

| Path | Git remote | Driver |
|---|---|---|
| Workspace root excl. `rooms/` — `identity_agent.json`, `memory/`, `notes/`, …, `hosts/<H>/**` | personal vault git remote | `sync-engine.sh sync` |
| `rooms/<room-id>/**` | room vault (one per room, registered in `identity_agent.json#rooms[]`) | `sync-engine.sh sync` (loops subscribed rooms) |

`rooms/` itself is a meta-dir — not committed to the personal vault. Each `rooms/<X>/` is its own git worktree.

#### §2.5.2 LOCAL exclusion (default-deny gitignore)

The managed `.gitignore` allows only the durable allowlist; everything else is excluded by default. `hosts/<H>/local/**` is gitignored in every scope.

Two carve-outs make the layout discoverable in git:
- `!hosts/<H>/local/**/` — re-include directories (so git walks into them)
- `!hosts/<H>/local/**/README.md` and `!hosts/<H>/local/**/.gitkeep` — keep per-folder layout markers tracked even when the data inside is not.

#### §2.5.3 Read-union semantics (LOCKED R-1)

**Sync is per-scope, READ is union across scopes.** This is v0.6's central rule, carried forward.

**Applies to AGENT and ROOM tiers.** LOCAL and MACHINE stay scope-isolated — runtime + per-host state is meaningless to merge across scopes.

**Read path** (agent context loader; runs at startup or on-demand):

```python
def load_concept(concept):  # concept ∈ {memory, notes, skills, context, assets, logs}
    facts = []
    # AGENT (personal)
    facts += walk(f"$WORKSPACE/{concept}/", scope="personal", tier="AGENT")
    # ROOM (each subscribed room)
    for room in list_rooms("$WORKSPACE/rooms/"):
        facts += walk(f"$WORKSPACE/rooms/{room}/{concept}/", scope=room, tier="ROOM")
    # MACHINE (this host only)
    facts += walk(f"$WORKSPACE/hosts/{my_hostname}/{concept}/",
                  scope=f"host:{my_hostname}", tier="MACHINE")
    return merge_with_provenance(facts)
```

**Provenance is automatic** — every fact carries the scope its path lives in (`personal`, `<room-id>`, or `host:<my-hostname>` for demoted entries). Agents surfacing a fact MUST display its provenance.

**Conflict handling** (same slug in two scopes): surface both with scope tags; do not silently overwrite. Scope priority for tiebreak: `personal > most-recently-active-room > others`.

**Asymmetric flow** — this is a feature:
- **Room → Personal**: automatic via read-union. Joining a room enriches your agent's knowledge.
- **Personal → Room**: explicit publish/lift. Private stuff doesn't leak to team contexts.

**Why room read-union matters operationally**: when your agent works on a personal task, it automatically picks up room-A's "use TypeScript strict mode" convention — no manual lift, no copy, no staleness.

#### §2.5.4 Memory subsystem — symlink + demotion-on-conflict (LOCKED M-1..M-4)

Memory has a special arrangement because Claude Code's own layer at `~/.claude/projects/.../memory/` is the live writer — it doesn't know about v0.7 and shouldn't have to.

**Data flow**:

```
   ~/.claude/projects/.../memory/         ← Claude Code writes here (unchanged)
            ↑ symlink (M-1)
            │
   hosts/<H>/local/memory/                ← LOCAL (this disk's live memory)
            │  push: copy → memory/
            ▼
   memory/                                ← AGENT (cross-host shared mirror)
            │  pull: copy → local/memory/
            │  IF CONFLICT (M-2):
            ▼
   hosts/<H>/memory/                      ← MACHINE (per-host permanent sink)
                                            (conflicting files demote here, never re-merge)
```

**Push** (this host has writes to propagate):
1. Walk `hosts/<H>/local/memory/` (follows symlink → `~/.claude/.../memory/`).
2. For each file: copy to `memory/<filename>` (overwrite — local is source of truth).
3. `git add + commit + push` to personal vault.

**Pull** (fetch updates from other hosts):
1. `git pull` updates `memory/`.
2. For each updated file:
   - **No local divergence** → copy `memory/<file>` → `local/memory/<file>` (safe overwrite).
   - **Local also modified** → **CONFLICT** → demote both:
     - Move local version to `hosts/<H>/memory/<filename>` (M-3: keep original filename; read-union surfaces with `host:<H>` provenance).
     - Remove from `memory/` (commit with `demoted: <slug> due to <ts> conflict`).
     - Other hosts on next pull → see file deleted in `memory/` → if their local has it too → demote to their `hosts/<their-H>/memory/`.

**Why demotion-as-conflict-resolution is the right policy**: conflicts on memory facts are *meaningful divergence* — two hosts learned different things about the same slug. Forcing a merge fakes unanimity. Demoting to per-host preserves both versions accurately; read-union ensures each host's agent still sees its own version locally. The fact loses cross-host portability but gains correctness.

**Generalize (M-4)**: same symlink+demotion mechanism applies to ALL AGENT/ROOM-tier concepts (notes, skills, context, assets, logs). Phased rollout — memory first, others after the sync engine matures.

**Symlink first-time setup**: when `ensure_layout` runs and detects `~/.claude/projects/.../memory/` exists but `hosts/<H>/local/memory/` is absent:
1. `mkdir -p hosts/<H>/local/`
2. `ln -s ~/.claude/projects/.../memory/ hosts/<H>/local/memory`

If `hosts/<H>/local/memory/` exists as a real directory (legacy from `sync-memory.sh`): refuse to clobber, log FATAL, point owner at the migration script.

**Slug selection**: `ensure_layout` symlinks the Claude Code projects slug derived from `$SUTANDO_REPO_DIR` (e.g. `~/Documents/github/sutando` → `~/.claude/projects/-Users-qingyunwu-Documents-github-sutando/memory/`). Sutando's convention is "always launch claude from the repo cwd"; that slug is what the M-1 symlink targets. Memory in other slugs (one-off `claude` launches from other dirs) is NOT synced by v0.7. A health-check warning flags this if other slugs exist and contain memory content.

**Absorbs `sync-memory.sh`**: the existing `bash scripts/sync-memory.sh` is retired in Phase 2 of the v0.6 → v0.7 migration. The sync engine takes over.

#### §2.5.5 Secret-scan push-gate

Every push, sync engine runs a secret-scan over staged paths:

**Filename patterns**: `*.pem`, `*.key`, `id_rsa`, `id_dsa`, `id_ed25519`, `id_ecdsa`, `*credentials*`, `*credential*`, `*.kdbx`, `.env`.

**Content patterns**: AWS access keys, OpenAI keys, GitHub tokens, Slack tokens, Discord bot tokens.

A match ABORTS the push. No silent leaks.

#### §2.5.6 Auto-generated layout documentation

`ensure_layout` drops two scoped docs on first run:

1. **Workspace-root `CLAUDE.md`** — first-touch orient for agents whose cwd is the workspace (not the repo). Lists scopes, where-to-write table, env vars, task-bridge protocol.
2. **Per-folder `README.md`** in every layout dir (~24 folders) — `**Tier**: <LOCAL|MACHINE|AGENT|ROOM> · **Sync**: <none|cross-host|cross-member> · **Mandatory**: <yes|no>` header + what-goes-here / what-does-NOT + see-also link.

Both auto-generated from heredoc templates inside the sync engine. Idempotent: existing files never overwritten.

Because directory names no longer encode tier (it's path-derived), the README header is the **single source of in-place tier signal** for someone navigating the tree.

#### §2.5.7 cwd-overlay (NEW — opt-in subsystem)

**Opt-in env var**: `SUTANDO_WORKSPACE_OVERLAY=on`. Default off → v0.6-style behavior unchanged. Independent of `SUTANDO_WORKSPACE_SYNC=on` — they compose.

**Why**: keeps workspace canonically outside `cwd` (preserving §2.2 separation) AND surfaces workspace content to Claude Code's native cwd-anchored discovery. Brings 7 content-anchored cwd privileges (CLAUDE.md, `.claude/settings.json`, project skills / commands / agents, `.mcp.json`, plugin discovery) to bear on workspace content without sacrificing the multi-writer architecture.

**Mount point**: `$SUTANDO_REPO_DIR/.workspace-mount/` (gitignored). The "mount" naming is deliberate, to reduce the `rm -rf` accident risk (see §2.5.7.3 risk R1).

**What gets mounted**:

```
<cwd>/.workspace-mount/
├── memory/             ← symlink → $SUTANDO_WORKSPACE/memory/
├── notes/              ← symlink
├── skills/             ← symlink
├── context/            ← symlink
├── assets/             ← symlink
├── logs/               ← symlink
├── public/             ← symlink → $SUTANDO_WORKSPACE/public/
│
├── rooms/              ← symlink per active room
│   ├── room-A/         ← symlink → $SUTANDO_WORKSPACE/rooms/room-A/
│   └── room-B/         ← symlink
│
└── hosts/<this-H>/<concept>/   ← symlink (own host's MACHINE slice)
                                  (other hosts' MACHINE NOT mounted —
                                   irrelevant to this host's agent)

EXCLUDED (intentionally absent from mount):
  - $SUTANDO_WORKSPACE/hosts/<*>/local/    LOCAL tier — bridges write here directly
  - $SUTANDO_WORKSPACE/hosts/<other>/      Other hosts' MACHINE — irrelevant locally
```

LOCAL stays in `$SUTANDO_WORKSPACE/hosts/<H>/local/` as v0.7's canonical home — bridges + watchers + daemons continue writing there. The mount is **read-from-the-agent's perspective** (agent works via `<cwd>/.workspace-mount/` paths; writes propagate back through the symlinks to `$SUTANDO_WORKSPACE/`); writes to LOCAL never go through the mount.

Skills-overlay (§2.5.8) is a separate concern that fires on top of the mount — symlinks/cps into `<cwd>/.claude/skills/<name>/` for native discovery.

##### §2.5.7.1 Choice of mount mechanism — symlink vs cp

Per-content-type split (decision 2026-05-31):

| Content type | Mount via | Why |
|---|---|---|
| `memory/`, `notes/`, `context/`, `assets/`, `logs/`, `public/`, `rooms/<X>/{...}/`, `hosts/<H>/{...}/` | **symlink** | Single source of truth (writes go straight to workspace; sync engine sees one location); zero startup latency; zero disk doubling; `git clean -dfx` removes only the symlink, not target; matches §2.5.4 memory M-1 pattern. |
| Skills / commands / agents / `.mcp.json` content that NEEDS native cwd-discovery | **cp** (§2.5.8 details) | Claude Code's project slug determination may canonicalize path through symlinks → skill registered to the wrong slug. cp gives deterministic slug at the cost of needing sync-back on shutdown. Pending R2 empirical verification (§2.5.7.3) — if symlinks turn out slug-stable for skills, downgrade to symlink. |
| CLAUDE.md fragment from workspace | **app-layer inject** (NOT mount) | Owner's existing `system-prompt` append channel; avoids `<cwd>/CLAUDE.md` overwrite conflict with the repo's CLAUDE.md. v0.7 does NOT modify CLAUDE.md auto-discovery behavior — workspace's auto-gen CLAUDE.md (§2.5.6) is read by Sutando app code at session start and prepended via `--append-system-prompt-file`. |

Git-as-diff is **how the symlinked content's UPSTREAM stays current** (workspace dir is a git working tree per §2.5.1; `sync-engine.sh pull/push` keep it fresh). The mount doesn't itself do incremental fetch — that lives one layer up in the workspace's own git lifecycle. Net effect: zero-latency mount + workspace git stays current via existing sync engine.

##### §2.5.7.2 Lifecycle

```bash
# Startup — sutando-app or src/startup.sh, before claude is launched
if [ "${SUTANDO_WORKSPACE_OVERLAY:-off}" = "on" ]; then
  bash "$SUTANDO_REPO_DIR/scripts/mount-workspace-overlay.sh"
fi
exec claude --add-dir "$SUTANDO_WORKSPACE" --add-dir "$HOME" \
            --append-system-prompt-file "$WORKSPACE_CLAUDE_MD_FRAGMENT" \
            "$@"

# At session end (existing SessionEnd hook from PR #1374)
bash "$SUTANDO_REPO_DIR/scripts/sync-workspace.sh" push  # already covered by §2.5
# Optional: bash scripts/unmount-workspace-overlay.sh  (cleans the gitignored symlinks)
```

`mount-workspace-overlay.sh` is idempotent — re-running on a populated mount no-ops; running for the first time on an empty `.workspace-mount/` creates the directory + symlinks. Atomic at the dir level: each symlink is `ln -snf` (force replace).

`.gitignore` entry (committed in repo): `/.workspace-mount/` — full subtree.

##### §2.5.7.3 Risks + mitigations

🔴 **R1. `rm -rf .workspace-mount/` accidents destroy workspace data**
Symlinks point at real workspace data. A user (or buggy script) doing `rm -rf .workspace-mount/` follows symlinks via `find -delete` semantics on some tools.
- **Mitigation 1**: name `.workspace-mount/` (not `.cache/` / `.overlay/`) — explicit semantic.
- **Mitigation 2**: drop a README.md inside the mount on first creation: *"This is a SYMLINK MOUNT — `rm -rf` here destroys workspace data. To detach, use `unlink` per file or `bash scripts/unmount-workspace-overlay.sh`."*
- **Mitigation 3**: ship `scripts/unmount-workspace-overlay.sh` that explicitly `unlink`s each symlink and leaves the dir empty — discourages the brute-force route.
- **Note**: `rm -r` (not `-rf`) on a dir of symlinks asks before removing each; only `-rf` is dangerous. Document `-r` as the safe variant.

🔴 **R2. Project slug canonicalization for native-discovery content**
Claude Code may resolve symlinks to canonical path when computing project slug for skill registration. Symptom: skill from `<cwd>/.claude/skills/foo` (where `foo` is a symlink to `$WORKSPACE/skills/foo/`) registers under workspace's slug, not the repo's. This needs **empirical verification** before committing to symlink-for-skills.
- **Mitigation**: §2.5.8 uses **cp** (not symlink) for skills/commands/agents/MCP until verified. Workspace dir stays mutable; cp gives a deterministic in-repo file for slug determination. Sync-back on shutdown handles agent-authored edits.
- **Future**: if Claude Code documents symlink-stable slug semantics, downgrade from cp to symlink uniformly.

🟡 **R3. CLAUDE.md ancestor discovery via symlinks**
If user `cd <cwd>/.workspace-mount/sub/dir/`, Claude Code's ancestor discovery might walk into `$WORKSPACE/...` (via the symlink target's canonical path) and pick up a CLAUDE.md there.
- **Mitigation**: v0.7 does NOT mount workspace CLAUDE.md at any subdir level. Auto-gen workspace CLAUDE.md (§2.5.6) is delivered via `--append-system-prompt-file`, not via mount. Document: users should not `cd` into `.workspace-mount/` subtree from inside claude; the mount is for the agent's tools, not for the shell-level cd.

🟡 **R4. Multi-host symlink + multi-host MACHINE tier**
Each host has its own `hosts/<this-H>/` slice. The mount only includes the local host's MACHINE — never another host's. Cross-host MACHINE visibility (if needed) goes through §2.5.3's read-union loader at app layer, not through the cwd-anchored mount.
- **Document**: agents writing to `.workspace-mount/hosts/<H>/<concept>/` are writing to THEIR host's slice. Cross-host writes must go through explicit app-layer dispatch.

🟢 **R5. Tools that don't follow symlinks**
`find -P` (default), `du --max-depth`, `rsync -l` — these stop at the symlink. Sutando's internal scripts using `find <cwd>` on the mount need `-L`. Document once in §2.5.7.6 (style guide).

🟢 **R6. Build / test cycle pollution**
CI in the repo runs `npm test` from cwd. With the mount present, scripts that walk `<cwd>/` see symlinked workspace content. **Mitigation**: CI runs with `SUTANDO_WORKSPACE_OVERLAY=off`. Belt-and-suspenders: `tests/` setup explicitly checks `find <cwd> -name .workspace-mount -prune` or similar.

##### §2.5.7.4 Performance / latency

- Startup mount: ~10 symlinks (root + N rooms + hosts<this-H> subdirs). Each `ln -snf` is sub-millisecond. **Sub-100ms total** even with 50 rooms.
- Steady-state: zero overhead — symlinks are kernel-level path resolution, O(1) cached.
- `git status` in repo: `.workspace-mount/` gitignored → not walked. Native git treats symlinks-to-outside-tree as untracked-ignored.
- `fswatch` in repo: existing watchers on `$SUTANDO_WORKSPACE/...` (not on `<cwd>/.workspace-mount/`) — unaffected.

##### §2.5.7.5 Coding style

- Any script walking `<cwd>` that should NOT recurse into mount: `find <cwd> -name .workspace-mount -prune -o -<rest>`.
- Any script walking mount that SHOULD follow symlinks: `find -L <cwd>/.workspace-mount/`.
- Tools that resolve to canonical path for any reason (slug, hash, IDs): explicitly note in code comment which behavior is required.

#### §2.5.8 skills-overlay (cp variant)

For content that benefits from Claude Code's native cwd-discovery: skills, commands, agents, `.mcp.json`. Today's empirical caveat (R2) keeps these as **cp** until symlink-stable slug semantics are verified.

```
$SUTANDO_WORKSPACE/skills/*/             ──cp──→  $SUTANDO_REPO_DIR/.claude/skills/<scope-prefix>-<name>/
$SUTANDO_WORKSPACE/rooms/<X>/skills/*/   ──cp──→  $SUTANDO_REPO_DIR/.claude/skills/room-<X>-<name>/
$SUTANDO_WORKSPACE/commands/*            ──cp──→  $SUTANDO_REPO_DIR/.claude/commands/...   (if commands/ ever ships skills-level entries)
$SUTANDO_WORKSPACE/.mcp.json fragments   ──merge──→  $SUTANDO_REPO_DIR/.mcp.json (single file constraint)
```

- **Prefix scheme** for slug-collision avoidance:
  - Personal scope: `ws-<name>` for AGENT-tier; e.g. `ws-quarterly-review`.
  - Room scope: `room-<room-id>-<name>`; e.g. `room-team-alpha-deploy-checklist`.
  - **Why prefix**: avoids repo-shipped skill `skills/email-helper/` colliding with a workspace `skills/email-helper/`.

- **Conflict rule** for `.mcp.json` (only one allowed at cwd root): merge MCP server lists; workspace entries take precedence over repo entries on same `name` key.
- **Sync-back**: if agent edits a copied skill (e.g., `SKILL.md` tweak mid-session), `unmount` hook diffs `<cwd>/.claude/skills/ws-*` against `$SUTANDO_WORKSPACE/skills/` and commits/pushes the delta to workspace's git. (Workspace then propagates to other hosts via §2.5 sync engine.)
- **gitignore**: `/.claude/skills/ws-*/` and `/.claude/skills/room-*/` patterns in repo `.gitignore`. Repo-shipped skills (no prefix) remain tracked.

## Part 3. The whole design picture

### 3.1 What v0.7 solves

The user collaborates AND wants Claude Code's native cwd-anchored mechanisms (skills, commands, MCP) to activate over their workspace content. v0.7 codifies this with a **2-axis** model (scopes × tiers, path-encoded) AND an **opt-in cwd-overlay** that surfaces AGENT/MACHINE/ROOM content to native discovery without sacrificing the multi-writer architecture.

### 3.2 Architecture in one picture

```
   ┌──────────────────────────────────────────────────────────┐
   │  $SUTANDO_WORKSPACE   (= YOU, the user — AGENT scope) │
   │                                                           │
   │   identity_agent.json                                     │
   │   memory/, notes/, skills/, ...                           │  ← AGENT
   │                                                           │     (lives at root; tier from path)
   │                                                           │
   │   ┌──────────────────────┐    ┌──────────────────────┐    │
   │   │ rooms/               │    │ hosts/               │    │  ← peer subdirs:
   │   │  virtual context     │    │  physical context    │    │     scope extensions
   │   │                      │    │                      │    │
   │   │  <room-A>/           │    │  <hostname>/         │    │
   │   │   identity_room.json │    │   identity_machine.. │    │
   │   │   memory/, notes/,...│    │   memory/, notes/,…  │    │  ← MACHINE
   │   │   members/<id>/      │    │   local/             │    │  ← LOCAL (this disk)
   │   │   (AGENT or ROOM)    │    │   (NEVER syncs)      │    │
   │   └──────────────────────┘    └──────────────────────┘    │
   └──────────────────────────────────────────────────────────┘
                            │
                            │  if SUTANDO_WORKSPACE_OVERLAY=on:
                            ▼
   ┌──────────────────────────────────────────────────────────┐
   │  $SUTANDO_REPO_DIR/.workspace-mount/   (gitignored)      │
   │                                                           │
   │   memory/, notes/, skills/, ...   ← symlinks → workspace │
   │   rooms/<X>/, hosts/<this-H>/<concept>/    (same)        │
   │                                                           │
   │   (LOCAL excluded — bridges keep writing to workspace)   │
   └──────────────────────────────────────────────────────────┘
                            │
                            │  Claude Code's native cwd-discovery activates over mount contents
                            ▼
   ┌──────────────────────────────────────────────────────────┐
   │  <cwd>/.claude/skills/ws-<name>/  (cp from workspace)    │
   │  <cwd>/.mcp.json                  (merged from workspace)│
   │  <cwd>/CLAUDE.md                  (REPO's; workspace's   │
   │                                   appended via flag)     │
   └──────────────────────────────────────────────────────────┘

   Workspace root = AGENT scope itself (not a peer of rooms/hosts).
   rooms/ and hosts/ are subdirs OF the personal workspace.
   Tier is the path the data lives in.

   Sync: each scope (personal vault, each room vault) independent.
   Read: union across personal + rooms + own host slice (R-1).
   Conflict: demote to per-host MACHINE (M-1..M-4).
   Overlay: opt-in mount of workspace content into cwd for native discovery.
```

### 3.3 Three orthogonal axes (a meta-invariant)

| Axis | Values | Manifestation |
|---|---|---|
| **Public/Private** | Code repo (public) vs Workspace + vaults (private) | §2.2 two-space split |
| **Scope** | personal vs `<room-id>` | path prefix |
| **Tier** | LOCAL / MACHINE / AGENT / ROOM | parent-path location |

A single file's location is the cross-product of these three. The mapping is dense (most cells have a path); the few empty cells are deliberate (e.g., no LOCAL inside rooms — rooms have no runtime; no MACHINE inside rooms — rooms have no physical machines).

### 3.4 Four invariants

1. **Write is scoped, read is unioned** (AGENT and ROOM tiers only). The sync vault only sees writes from its scope; the agent's knowledge surface sees facts from all scopes you've opted into.
2. **Conflicts demote, never silently merge**. Two divergent hosts' versions of the same slug both survive — as host-local — instead of one overwriting the other or pretending they were unanimous.
3. **LOCAL is sacred ground**. Live tasks, runtime state, secrets — all this stays on the physical disk. No vault, no sync, no broker. No mount (overlay excludes it).
4. **Workspace root identity is portable**. `identity_agent.json` at root names YOU across all hosts and all rooms. Devices change, room memberships change; the user identity is the anchor.

### 3.5 Voice-note end-to-end (worked example, paths in C-form)

A user dictates "team-A uses TypeScript strict mode" while sitting at mac-mini, in the middle of a coding session for team-A's project.

1. Voice agent transcribes → produces a memory write candidate.
2. Promotion skill classifies: scope = `room-A` (team-A's room), tier = AGENT (cross-host within the room) → ROOM in v0.7 lingo. Path: `rooms/room-A/memory/team_a_conventions.md`.
3. File lands in this host's local `rooms/room-A/...` directly (worktree is local).
4. Next `sync-engine sync` push: room-A vault gets the new commit.
5. Alice (also in team-A) on her laptop runs `sync-engine sync pull`: receives the file.
6. Alice's agent loads memory: walks personal + `rooms/room-A/memory/` → the convention is now visible to her agent with `scope=room-A` provenance.
7. Alice starts a personal task ("review my own code"): agent context already knows team-A's TS-strict convention from her room-A subscription. No manual lift.

### 3.5.1 Worked example with cwd-overlay opt-in

User wants Sutando to gain a "quarterly-review" skill that's specific to *their* workflow (not shared via repo).

1. User creates `$SUTANDO_WORKSPACE/skills/quarterly-review/SKILL.md` + scripts.
2. `sync-engine.sh push` commits + pushes to personal vault.
3. **Without overlay**: skill is in workspace but Claude Code doesn't auto-register it. Sutando would need an app-layer skill loader to inject it into the system prompt. None exists today → skill silently invisible.
4. **With overlay** (Phase 4+, `SUTANDO_WORKSPACE_OVERLAY=on`): next session start, `mount-workspace-overlay.sh` cps it to `<cwd>/.claude/skills/ws-quarterly-review/` → Claude Code auto-registers `/ws-quarterly-review` slash command → immediately invocable. Same flow on mini after sync.
5. User edits skill prompt mid-session via the agent. Edit lives in `<cwd>/.claude/skills/ws-quarterly-review/SKILL.md`. On session end, `unmount-workspace-overlay.sh` diffs vs `$WORKSPACE/skills/quarterly-review/SKILL.md`, prompts for sync-back commit. Next time, the upstream is current.

### 3.6 Non-goals

- **Cross-room federation** (one room reading another). Out of scope. Each room is its own vault; rooms don't subscribe to each other.
- **Real-time collaboration** (live cursors, conflict-free CRDTs). v0.7 is eventual-consistent via git; tighter synchrony lives in the PipeRoom protocol, not the workspace contract.
- **Public discoverability of rooms**. Rooms are private to their members; discovery is via invite (broker, manifest pull, or out-of-band).
- **v0.7 overlay as default**. Off by default; opt-in. Single-machine / non-customizing users see zero overhead.
- **Overlay-as-canonical**. Workspace remains the source of truth; mount is a view.

### 3.7 Migration (recap from §2.6)

Phase 0 → Phase 1 (naming sweep) → Phase 2 (dual-resolve) → Phase 3 (per-host activate) → Phase 4 (overlay opt-in) → Phase 5 (retire dual-resolve). Phase 3 has a per-host sign-off gate; no automatic rollout. Existing personal data does not move under naming sweep (pure `mv`).

### 3.8 What ships with v0.7

- `sync-engine.sh` — the converged sync engine specified in §2.5 (room subscriptions, read-union loader, symlink+demotion machinery).
- `mount-workspace-overlay.sh` + `unmount-workspace-overlay.sh` — opt-in cwd-overlay (§2.5.7 + §2.5.8). Default off.

## Appendix B. Why not hardlink for the overlay mount

Considered. Hardlinks don't span filesystems (mac / external drive case), don't work for directories (mount needs symlink anyway for dir-level pointers), and don't carry "symlinkness" — programs can't tell the file is a mount. Symlinks make the mount-vs-real distinction visible to inspection (`ls -la` shows the arrow). Keep symlinks.
